# decant
Generate TypeScript types from JSON Schema files and OpenAPI documents, with strict schema checks and the same types Juniper infers.

[![npm package](https://badge.fury.io/js/decant.svg)](https://www.npmjs.com/package/decant)
[![License](https://img.shields.io/npm/l/decant.svg)](https://github.com/JacobLey/leyman/blob/main/apps/decant/LICENSE)

</div>

- **Types that match the schema** — tuples (`prefixItems`), `oneOf` unions you can narrow, `patternProperties` keys like `` `x-${string}` ``, recursive `$defs` and `if`/`then`/`else` all become precise types, not `any` or `unknown[]`.
- **Round-trips Juniper** — a schema built with [Juniper](https://www.npmjs.com/package/juniper), serialized and read back by decant, gives the same type Juniper inferred. Every release is tested against that.
- **Strict by default** — unknown keywords, keywords that don't apply to the schema's type, undeclared `required` properties, and contradictions like `minLength` over `maxLength` fail generation, instead of silently changing what the schema accepts. Without strict mode, the type follows exactly what a validator accepts.
- **One file from many** — `$ref`s to other files and URLs are loaded and generated into the same output, with `$id` and `$anchor` resolved as the spec says.
- **Generated files stay in sync** — a `--ci` mode fails when a committed file is out of date, like [populate-files](https://www.npmjs.com/package/populate-files).
- **Types only** — the output is plain TypeScript types, with no runtime dependency.

For the motivation, and how it compares to other generators, see [WHY-DECANT.md](https://github.com/JacobLey/leyman/blob/main/apps/decant/WHY-DECANT.md).

## Install

```sh
npm i -D decant
```

## Example

`user.json`:

```json
{
  "type": "object",
  "properties": {
    "id": { "type": "string", "pattern": "^usr_" },
    "home": { "$ref": "#/$defs/Address" },
    "point": {
      "type": "array",
      "prefixItems": [{ "type": "number" }, { "type": "number" }],
      "items": false,
      "minItems": 2
    }
  },
  "required": ["id"],
  "$defs": {
    "Address": {
      "type": "object",
      "properties": { "city": { "type": "string" } },
      "required": ["city"]
    }
  }
}
```

```sh
npx decant user.json --name User
```

`user.ts`:

```ts
// Generated by decant from a JSON Schema. Do not edit by hand, regenerate it instead.

export type User = {
    id: `usr_${string}`;
    home?: Address;
    point?: [number, number];
};

export type Address = {
    city: string;
};
```

## Usage

decant is an ESM module, and a CLI. Most projects run the CLI as a build step, and commit the generated file. In CI, `--ci` (on by default when the `CI` environment variable is set) fails instead of writing when the file is out of date.

The programmatic API is the same: `decant(schema)` returns the TypeScript source, and `decantFile(path)` reads a schema file and writes the types next to it.

The root schema becomes a type named `Schema` (or `--name`). Every definition in the root `$defs` (or draft 7 `definitions`) becomes an exported type named after its key, in PascalCase. A schema referenced by `$ref` from elsewhere in the document becomes a named type too, named after its key in any nested `$defs`, or else after its path. Everything else is inlined.

### References to other files

A `$ref` may point at another file, or a URL, relative to the schema it is in: `{ "$ref": "./address.json" }`, `{ "$ref": "https://example.com/schemas/user.json#/$defs/Name" }`. The CLI and `decantFile` load each one, and everything it references in turn, and the output is still one file:

- Each referenced file becomes a type named after its `title`, or else its file name (`address.json` is `Address`). Two of the same name are numbered (`Address2`).
- A file referenced twice is one type.
- A file that only holds `$defs` (shared definitions) is not a type itself, but its definitions are, when referenced.
- Files without a `$schema` are read in the input's dialect: JSON Schema 2020-12, or the OpenAPI version of an OpenAPI document.
- A file or URL that can't be loaded throws a `DecantLoadError`.

Loaded files are embedded with an absolute `$id`, following the bundling process of JSON Schema 2020-12, so `$ref`s resolve to them unchanged, and `$id` and `$anchor` inside them work as in the original files. `--no-fetch` (or `fetch: false`) loads files only, never URLs. `decant()` itself reads one document, and doesn't load anything: bundle first, or use `decantFile`.

### OpenAPI documents

An OpenAPI 3.0 or 3.1 document (a JSON or YAML file with an `openapi` version) is read too. Each of its `components.schemas` becomes an exported type named after its key, and there is no root type. The version decides the dialect: 3.0 schemas may use `nullable`, and 3.1 schemas are JSON Schema 2020-12. Either may use OpenAPI's own keywords (`discriminator`, `xml`, `externalDocs`, `example`), which don't change the type.

```sh
npx decant openapi.yaml -o src/api-types.ts
```

### YAML

A `.yaml` or `.yml` file is read as YAML 1.2, whether it is the input or a file it references, and so is a URL served with a YAML media type. Anchors and aliases are expanded, and merge keys (`<<: *base`) merged. An alias inside the schema it names, a recursive schema, becomes a `$ref` to that schema, so it is a recursive type. Anything else JSON can't hold is an error: an alias inside a value that isn't a schema (such as a `const`), tags beyond YAML's core schema (such as `!!binary`), keys that aren't strings, duplicate keys, and `.inf` or `.nan`.

The generated file is formatted with [format-file](https://www.npmjs.com/package/format-file), using your project's Biome or Prettier config if either is installed.

## Precise types

Where other generators commonly lose type information, decant keeps it:

| Schema | decant | Often generated instead |
|---|---|---|
| `prefixItems: [{ number }, { number }]`, `items: false` | `[number, number]` | `never[]`, `any[]`, or `[number, number, ...number[]]` |
| `oneOf` of objects with a `kind` const | a union that narrows on `kind` | one object, with each branch's properties optional, or `any` |
| `pattern: "^usr_"` | `` `usr_${string}` `` | `string` |
| `patternProperties: { "^x-": string }`, `additionalProperties: false` | `` { [key: `x-${string}`]: string } `` | `{ [k: string]: unknown }`, or `string` for every key |
| recursive `$defs` | recursive named types | `any` after a few levels, or `undefined` |
| `enum: ["a", 42, null]` | `"a" \| 42 \| null` | `string \| number \| null` |

Each row is one of the probes in [WHY-DECANT.md](https://github.com/JacobLey/leyman/blob/main/apps/decant/WHY-DECANT.md#compared-to-alternatives), which compares decant with five other tools on the same schema.

## How schemas become types

| JSON Schema | TypeScript |
|---|---|
| `true`, `{}` | `unknown` |
| `false`, `{ "not": {} }` | `never` |
| `type` | `string`, `number` (also `integer`), `boolean`, `null`; a `type` array is a union |
| `pattern` of a literal prefix, suffix or substring (`^abc`, `abc$`, `abc`) | `` `abc${string}` ``, `` `${string}abc` ``, `` `${string}abc${string}` `` |
| any other `pattern`, `format`, lengths, ranges | the plain type, as TypeScript can't express them |
| `enum`, `const` | literal types, including objects and arrays |
| `items` | `T[]` |
| `items` + `minItems` up to 3 | `[T, ...T[]]`, with `minItems` leading items. Larger values stay `T[]` (see `typedMinItems`) |
| `prefixItems` + `items: false` | `[A, B]`, with items beyond `minItems` optional |
| `prefixItems` + `items` | `[A, B, ...T[]]` |
| draft 7 `items` array + `additionalItems` | same as `prefixItems` + `items` |
| `properties` + `required` | `{ a: A; b?: B }` |
| `additionalProperties: true` / schema | `[key: string]: unknown` / `T` |
| `patternProperties` | an index signature, keyed by `` `x-${string}` `` for a literal prefix like `^x-`, or `string` otherwise |
| `type: "object"` with no properties | `Record<string, unknown>` |
| `dependentRequired`, `dependentSchemas`, draft 7 `dependencies` | `{ a?: never } \| { b: B }` |
| `allOf` | intersection |
| `anyOf`, `oneOf` | union |
| `if` / `then` / `else` | `(If & Then) \| Else` |
| `not` of `null` or literal values | removes them from a union; any other `not` leaves the type |
| `$ref` | the referenced named type. It resolves against the nearest `$id`, so `#/$defs/A` inside an embedded resource is that resource's `A`, and may name an `$anchor` |
| `propertyNames` with a literal prefix or `enum` | the keys of `additionalProperties`: `` `x-${string}` ``, or optional properties `a`, `b` |
| `title`, `description`, `deprecated` | JSDoc |
| `default`, `examples`, `format`, and constraints such as `minLength` or `maximum` | JSDoc tags, e.g. `@minLength 3`, so editors show them |

Subschemas of `allOf`, `anyOf`, `oneOf`, `if`/`then`/`else` and `not` without a `type` of their own apply to their parent's types, as Juniper writes them. So `{ "type": ["string", "null"], "allOf": [{ "pattern": "^a" }] }` is `` `a${string}` | null ``.

Without `additionalProperties`, an object type has no index signature: TypeScript objects already allow other keys, and reading an undeclared key stays an error.

### Not supported

- `$dynamicRef` and `$recursiveRef` throw `DecantUnsupportedError`. `decant()` only reads one document, so with it, a `$ref` to another file does too (see [References to other files](#references-to-other-files)). References may use `$id` and `$anchor`.
- `unevaluatedProperties`, `unevaluatedItems` and `contains` are accepted, but don't change the type.
- OpenAPI's `discriminator` is accepted, but not checked against the `oneOf` branches. The branches still narrow on the property as a union does.
- Swagger 2.0 documents.

### Differences from Juniper

decant is tested to generate the same type Juniper infers, for Juniper schemas covering each of its schema types and keywords. The exceptions are where the JSON says more than Juniper's type does, or less:

- An object schema with no properties is `Record<string, unknown>`, not Juniper's empty object type.
- Prefix items beyond `minItems` are optional. Juniper's `tupleSchema()` always sets `minItems`, so its tuples are identical.
- In `if`/`then`/`else`, a property set to `false` in `else` is `?: never`.
- A type from `.cast<T>()` or `customSchema<T>()` exists only in TypeScript, so decant reads the JSON it emits instead.

## Strict mode

Strict mode (the default) fails with a `DecantStrictModeError` on schemas that are valid JSON Schema, but most likely mistakes. Validators ignore these, so the schema silently accepts more, or less, than it appears to.

Keywords that do nothing:

- An unknown keyword. Keywords starting with `x-` are allowed, as are OpenAPI's keywords in an OpenAPI document or with `openApi30`.
- A type specific keyword (e.g. `maxLength`) in a schema without a `type`, or whose `type` it doesn't apply to (e.g. `maxLength` on a number). Subschemas inherit their parent's type.
- A `required` property that isn't in `properties`, of the schema or a parent.
- `then` or `else` without `if`.

Schemas that accept nothing, or less than they declare:

- `minLength` greater than `maxLength`, and the same for `minItems`/`maxItems`, `minProperties`/`maxProperties` and `minContains`/`maxContains`.
- `minimum`/`exclusiveMinimum` and `maximum`/`exclusiveMaximum` that no number (or no integer, for `integer`) fits between.
- An `enum` or `const` value that isn't of the schema's `type`.
- A `required` property whose schema is never valid (e.g. `false`), or more required properties than `maxProperties` allows.
- `minProperties` more than an object with `additionalProperties: false` can have.
- A tuple (`prefixItems` with `items: false`) shorter than `minItems`, or longer than `maxItems`.
- A `$ref` back to a schema it is part of, without a property or item in between, such as `{ "anyOf": [{ "$ref": "#" }, { "type": "string" }] }`. It applies to the same value again, so a validator never finishes checking it, and JSON Schema leaves its behaviour undefined.

Every schema Juniper builds passes.
- A `$ref` back to a schema it is part of, without a property or item in between, such as `{ "anyOf": [{ "$ref": "#" }, { "type": "string" }] }`. It applies to the same value again, so a validator never finishes checking it, and JSON Schema leaves its behaviour undefined.

### Without strict mode

Disable strict mode (`strict: false`, `--no-strict`) for schemas you don't control. The generated type then follows what a validator accepts, and is never narrower:

- Unknown keywords, and keywords that don't apply to the type, are ignored.
- A schema without a `type` accepts every type. `{ "properties": { "a": … } }` is the object type, or any string, number, boolean, `null` or array.
- A type whose constraints contradict each other is `never`. For `{ "type": ["string", "null"], "minLength": 3, "maxLength": 2 }`, only `null` is valid.
- Tuple items beyond `maxItems` are left out.
- A `$ref` back to a schema it is part of, without a property or item in between, is `never`: it can't be why a value is valid. The `anyOf` above is `string`. A schema it passes through on the way back is inlined, as TypeScript rejects a type that refers to itself outside an object or array.

## Stability of generated files
- A `$ref` back to a schema it is part of, without a property or item in between, is `never`: it can't be why a value is valid. The `anyOf` above is `string`. A schema it passes through on the way back is inlined, as TypeScript rejects a type that refers to itself outside an object or array.

The text of a generated file is not part of decant's API. Formatting, ordering, and how a type is written (e.g. `Record<string, number>` or `{ [key: string]: number }`) may change in any release.

The types TypeScript reads from it are. A change that makes a generated type accept or reject different values, or read differently (such as a union becoming an intersection), is a breaking change.

## API

### `decant(schema, options?)`

Generate TypeScript types from a JSON Schema.

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `schema` | `unknown` | — | Required. Parsed JSON Schema, or OpenAPI document. |
| `options.name` | `string` | `'Schema'` | Name of the root schema's type. Not used for an OpenAPI document. |
| `options.strict` | `boolean` | `true` | Fail on likely mistakes. See [Strict mode](#strict-mode). |
| `options.baseUri` | `string` | a placeholder | URI the schema was read from, which relative `$id`s and `$ref`s resolve against. |
| `options.typedMinItems` | `number` | `3` | Largest `minItems` typed as required items, e.g. `[T, ...T[]]`. `0` turns it off. The default matches Juniper. |
| `options.openApi30` | `boolean` | `false` | Read the schema as an OpenAPI 3.0 schema, which allows `nullable` and `example`. An OpenAPI document's own version is used instead. |

**Returns** `string` — TypeScript source, not formatted.

**Throws** `DecantError` — see [Errors](#errors).

```ts
import { decant } from 'decant';

decant({ type: 'array', items: { type: 'string' } }, { name: 'Tags' });
// export type Tags = string[];
```

---

### `decantFile(input, options?)`

Read a JSON Schema file, and write its types to a TypeScript file.

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `input` | `string` | — | Required. Path to the JSON Schema file. |
| `options.output` | `string` | input path with `.ts` instead of `.json` | Path of the TypeScript file to write. |
| `options.cwd` | `string \| URL` | `process.cwd()` | Directory relative paths resolve from. |
| `options.check` | `boolean` | `false` | Fail, rather than write, if the output file is not up to date. |
| `options.dryRun` | `boolean` | `false` | Do not write the output file. |
| `options.fetch` | `boolean` | `true` | Load `http:` and `https:` URLs the schema references. Otherwise only files are loaded. |
| `options.name`, `options.strict`, `options.openApi30`, `options.typedMinItems` | | | Same as [`decant`](#decantschema-options). |

**Returns** `Promise<{ output: string; updated: boolean }>` — absolute path of the output file, and whether its content changed.

**Throws** `DecantError` — see [Errors](#errors). With `check`, also throws if the file is out of date.

---

### Errors

Every error extends `DecantError`, with a `pointer` property: the JSON Pointer to the schema or keyword at fault, e.g. `#/properties/a/type`. The pointer is also at the end of the message.

| Error | Thrown when |
|-------|-------------|
| `DecantInvalidSchemaError` | The input is not a valid JSON Schema, e.g. `properties` is not an object, or a `$ref` does not resolve. |
| `DecantStrictModeError` | A [strict mode](#strict-mode) rule is broken. |
| `DecantUnsupportedError` | The schema uses a feature decant can't generate types for. See [Not supported](#not-supported). |
| `DecantLoadError` | A file or URL the schema references could not be loaded. Its `cause` is the underlying error, such as the file system's or the parser's, if there was one. |

## CLI

```sh
decant <input> [options]
```

| Option | Default | Description |
|--------|---------|-------------|
| `-o`, `--output` | input path with `.ts` | Path of the TypeScript file to write. |
| `--name` | `Schema` | Name of the root schema's type. Not used for an OpenAPI document. |
| `--strict` | `true` | Fail on likely mistakes. Disable with `--no-strict`. |
| `--typed-min-items` | `3` | Largest `minItems` typed as required items. `0` turns it off. |
| `--open-api-30` | `false` | Read the schema as an OpenAPI 3.0 schema. An OpenAPI document's own version is used instead. |
| `--ci` | `true` in CI | Fail if the output file is not up to date. Implies `--dry-run`. |
| `--dry-run` | `false` | Do not write the output file. |
| `--fetch` | `true` | Load URLs the schema references. `--no-fetch` loads only files. |
| `--cwd` | `.` | Directory relative paths resolve from. |

The path of a written file is logged. Nothing is logged when it was already up to date.

## Why "decant"?

[Juniper](https://www.npmjs.com/package/juniper) builds schemas with their types. Once serialized, a schema is bottled up as plain JSON, and its types are left behind. Decanting pours it back out into something you can use: the same types, restored.

It's also a nod to Juniper itself: juniper berries are what gives gin its flavor.

## Compared to alternatives

- [json-schema-to-typescript](https://www.npmjs.com/package/json-schema-to-typescript) — the most used generator. 2020-12 tuples become `never[]`, `pattern` is always `string`, and `patternProperties` open the object to `[k: string]: unknown`.
- [quicktype](https://www.npmjs.com/package/quicktype) — many languages, but merges `oneOf` objects into one type with optional fields, and widens `enum` numbers.
- [json-schema-to-zod](https://www.npmjs.com/package/json-schema-to-zod) — generates a validator, but every `$ref` becomes `z.any()`.
- [json-schema-to-ts](https://www.npmjs.com/package/json-schema-to-ts), TypeBox `Static` — infer types in TypeScript instead of generating them, so the schema has to be pasted into TypeScript `as const`. An imported `.json` file widens to `unknown`.

Tested side by side in [WHY-DECANT.md](https://github.com/JacobLey/leyman/blob/main/apps/decant/WHY-DECANT.md#compared-to-alternatives).
